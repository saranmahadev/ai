# CLAUDE.md

`AGENTS.md` (imported above) holds the vault rules, the change guardrail, and the vault-to-site mapping. This file is the technical guide to the site in `.site/`. Entries 1–32 of "Migration status" are history: they describe earlier versions of the site (planets, Play Mode, the 3D scenes) that entry 33 replaced.

## What this repo is

- An Obsidian vault of Markdown notes about AI (`*.md` at the root and in each course's folder).
- A static site called **AI Base** in `.site/` (the vault itself is the "AI Knowledge Brain") that publishes the vault as a free, open curriculum for learning AI in order: **courses**, each made of **chapters**, each made of **lessons**, every lesson with a worked example and an interactive bench. It is one flat, minimal document site in a milk, orange and brown palette, with a light and a dark theme. The vault is the source of truth; the site is derived.

## Commands (run in `.site/`)

```bash
npm ci              # install (dependency: marked; devDependency: playwright, for the test:* scripts below — also wires up the pre-push hook, see below)
npm run content     # build the vault into .site/content.json, then prerender static pages and the feed (see below)
npm run prerender   # just the static-page step (scripts/build-static.mjs: lesson/course/glossary pages, sitemap.xml, robots.txt, llms.txt, llms-full.txt)
npm run feed        # just the Atom feed step (scripts/build-feed.mjs → .site/feed.xml)
npm test            # build in memory and print content warnings (unresolved links, unassigned notes, missing bench modules, prerequisites out of order)
npm run test:benches  # opens every bench at 1280, 768 and 390px in Chromium, exercises its controls, fails on console errors or horizontal overflow; --shots=DIR saves screenshots
npm run test:reader   # exercises the lesson page in Chromium: type, the three columns, prerequisites, reading line, On this page, text size, read tracking, resume, ?at= links, previews, key terms, selection bar, the bench, dark, phone width; --shots=DIR
npm run test:site     # home and curriculum, a course page, search, glossary, My progress, cross-course tags, old links, 404, the theme switch and a prerendered page, in Chromium; --shots=DIR
npm run test:pwa      # manifest validity, service worker registration, and a visited lesson rendering after going offline, in Chromium; --shots=DIR
npm run dev         # build content and serve the site at http://localhost:8000
```

`content.json` is generated and gitignored. Deployment (`.github/workflows/deploy-site.yml`) runs `npm ci && npm run content`, then publishes `.site/` to the `web` branch, excluding build files.

There is no GitHub Actions check workflow: `npm ci`'s `prepare` script runs `git config core.hooksPath .githooks`, which points git at the committed `.githooks/pre-push` hook. That hook runs `npm test`, `npm run content` and all four `test:*` scripts before a push leaves the machine, but only on `dev` and `main` (see below) — it exits immediately on a `feature/*` branch. Skip it once with `git push --no-verify` if needed; don't disable it otherwise. The `test:*` scripts launch Playwright's own Chromium; set `PW_CHROMIUM=/path/to/chrome` to use a browser that is already installed instead.

## Branching and release flow

Three branches, each with one job:

| Branch | Role | Pre-push hook | Moves forward by |
| --- | --- | --- | --- |
| `feature/<name>` | All day-to-day development, branched from `dev`. | **Skipped** — pushes go straight through for fast iteration. | Merged into `dev` once the feature is ready. |
| `dev` | Integration/staging branch. Every finished feature lands here first. | **Runs** — the full suite (`npm test`, `npm run content`, all four `test:*` scripts) must pass before `dev` can be pushed. | Pushed to remote, then opened as a PR into `main`. |
| `main` | Production branch. Only moves via a merged PR from `dev`. | Runs too (a safety net; should already be green since it came from a tested `dev`). | Merging the PR triggers `.github/workflows/deploy-site.yml`, which publishes `.site/` to the `web` branch (ai.saranmahadev.in). |

Flow for a single change:

1. **Branch**: `git checkout dev && git pull && git checkout -b feature/<name>`.
2. **Develop**: commit freely on the feature branch. `git push` here skips the test suite entirely, so iteration stays fast.
3. **Integrate**: once the feature is ready, merge it into `dev` (`git checkout dev && git merge feature/<name>`).
4. **Test**: `git push origin dev` — this is where the full pre-push suite runs. A failure here is fixed on `dev` (or by going back to the feature branch) before `dev` can reach remote.
5. **Release**: open a PR from `dev` into `main`.
6. **Deploy**: merging that PR deploys automatically — there is no separate deploy step.

Never push straight to `main` from a feature branch, and don't habitually `--no-verify` past the hook on `dev` — `dev` is the one place the full suite is meant to catch problems before they reach production.

## Site architecture

```
.site/
  courses.json             the curriculum: an `overview` note and the `courses` in order (id, title, blurb, index note, folder; or `planned`)
  scripts/build-content.mjs  vault → content.json (courses, chapters, lessons, links, backlinks) + content/<id>.json (rendered HTML, table of contents)
  scripts/build-static.mjs  content.json → prerendered pages at real paths, plus sitemap.xml, robots.txt, llms.txt, llms-full.txt (see "Static prerendering")
  scripts/build-feed.mjs    content.json + one batched `git log` walk → feed.xml, the Atom feed of recently touched lessons
  index.html               the app shell: header, <main id="view">, footer, search dialog
  styles.css               the whole design system: tokens, light and dark, every page, the bench block
  theme.js                 light/dark: a tiny classic script in <head> (also the only script the prerendered pages carry)
  views.js                 page templates as pure functions (content → HTML strings), shared by main.js and build-static.mjs
  main.js                  hash router + behaviour: loads content.json, renders views, mounts benches and the reader
  reader.js                the lesson reading experience: reading line, On this page, text size, read/progress tracking, resume, previews, key terms, selection bar
  search.js                lesson search (titles, key terms, summaries, courses; / or Ctrl+K)
  manifest.json, sw.js, icon-192.png, icon-512.png  the PWA layer (see "Progressive Web App")
  content/                 generated per-lesson bodies (`<id>.json`: html, toc), gitignored; content.json holds only the index
  benches/                 interactive demos embedded in lessons: kit.js (shared helpers) + one module per bench id
  vendor/fonts/            Newsreader, Inter and JetBrains Mono (variable, latin, all OFL), vendored: the site makes no external requests
  favicon.svg, og.png      icon and 1200×630 social preview (regenerate og.png from a Playwright screenshot of the home page when visuals change; regenerate icon-192.png/icon-512.png the same way from favicon.svg)
```

- **Structure:** a **course** (a top-level folder, listed in `courses.json`) has **chapters** (its sub-folders); a chapter has an optional **intro** page (its landing note) and its **lessons** (the notes it links, in link order). Courses, chapters and lessons are numbered in learning order everywhere they appear. `content.json` is `{ overview, courses: [{ id, title, blurb, index, chapters: [{ id, title, intro, lessons }], lessonCount }], topics: { <id>: { title, course, chapter, summary, words, status, benches, glossary, links, backlinks, path } }, stats }`. A "topic" in the index is any published page: a lesson, a chapter intro, a course's landing note, or the overview (`ai`).
- **Style:** minimal and flat. Milk ground, espresso-brown ink, one orange accent used only for actions, progress and "where you are". No shadows on surfaces, no gradients, no emoji, hairline rules instead of boxes, 8px corners for controls and 12px for cards. Newsreader (serif) for titles and lesson text, Inter for interface text, JetBrains Mono for formulas and numerals. Every colour is a token on `:root` in `styles.css` (`--milk`, `--oat`, `--crust`, `--card`, `--ink`, `--cocoa`, `--muted`, `--orange`, `--link`); dark redefines the same tokens (brown ground, milk ink) both under `prefers-color-scheme: dark` and under `:root[data-theme="dark"]`, so keep the two dark blocks identical. Never hard-code a colour in a component rule; body text must stay at 4.5:1 or better in both themes (`--orange` is for fills and marks, `--link` for orange text).
- **Routing:** hash-based so it works on static hosting. `#/` home (the curriculum), `#/<course>` a course, `#/<course>/<slug>` a lesson (ids are `<course>/<slug-of-note-title>`; a chapter intro and a course's landing note are pages of the same shape; the overview note is `ai`), `#/<course>/glossary` and `#/glossary`, `#/progress`. Old links keep working: `#/explore`, `#/list` and `#/galaxy` render home, `#/path` renders My progress, and `#/search` opens the search box. `route()` checks `<course>/glossary` ahead of the lesson lookup, since a lesson id has the same shape.
- **Templates (`views.js`):** every page is a pure function of the content index, created by `createViews({ content, link, anchor, prose, read, progress, app })`. The app passes hash links and the reader's localStorage state with `app: true`; the static build passes path links, no reader state and `app: false` (which swaps "Mark as read" for a link into the app and drops controls that need JavaScript). Change a page in `views.js` and both outputs change together; do not add page markup to `main.js` or `build-static.mjs`. `index.html` carries the same header and footer as `siteHeader()`/`siteFooter()` by hand; keep them in step.
- **Pages:** home (promise, curriculum size, a Continue strip once something is read, the ten courses as one numbered list, the four-part lesson shape); course (number, blurb, progress panel with the next lesson, chapters as native `<details>` with read / up next / unread marks); lesson (chapter list on the left, article in the middle, "On this page" and text size on the right; under 1100px the right column goes, under 820px the chapter list moves below the article); glossary (course switcher, live filter, A–Z jump row, terms grouped by letter with their source lesson); My progress; 404.
- **Lesson page details:** the note's first paragraph is styled as the lede; its `**You need:**` line becomes a row of prerequisite chips (`polish()` in `views.js`), and a prerequisite from another course carries that course's name; breadcrumbs sit above the title; "Mark as read" and previous/next close the article. The note's own *Related* list is shown as written.
- **Theme:** `theme.js` sets `data-theme` on `<html>` from `localStorage` (`ai-base-theme`, `light` or `dark`) or leaves it unset to follow the system; the header button toggles it; `?theme=light|dark` forces it for one page load (used by tests and screenshots). It exposes `window.aiBaseTheme.isDark()` for the benches.
- **Reader state (this browser only):** `ai-base-read` (lesson ids read: reaching 90% of a lesson marks it, and so does the button; `markRead`/`markUnread`/`readSet`), `ai-base-progress` (furthest scroll fraction per lesson; `progressMap`), `ai-base-pos:<id>` (resume position), `ai-base-reader` (text size). Nothing is stored server-side.
- **Static prerendering:** a hash fragment (`#/math/logarithms`) is never sent to the server, so no crawler can be shown a distinct document per route on the app alone. `scripts/build-static.mjs` (run by `npm run content`, or alone via `npm run prerender`) writes a plain HTML page at a real path for every written lesson (`.site/<course>/<slug>/index.html`, served at `/<course>/<slug>/`), every course (`.site/<course>/index.html`) and course glossary (`.site/<course>/glossary/index.html`), the glossary index (`.site/glossary/`) and the curriculum (`.site/explore/`, kept at that path for existing links) — plus `sitemap.xml`, `robots.txt` and `llms.txt`. The pages come from the same `views.js` templates as the app, embed the lesson's actual body HTML with internal links rewritten from `#/id` to `/id/`, include `BreadcrumbList` + `Article` JSON-LD on every lesson (plus `FAQPage` from the Quick check `<details>` blocks, `Course` on course pages and `DefinedTermSet` on glossaries), and link into the app for progress tracking and the live bench. Their only script is `theme.js`; a bench's `fallback:` sentence is what a prerendered page shows in place of a mounted bench. The same script writes `llms-full.txt`: every written lesson's source note (frontmatter stripped), concatenated in course order straight from the vault files. These pages are generated output, gitignored like `content.json`; `GENERATED_DIRS` is derived from `courses.json`, so adding a course only needs a matching line in the root `.gitignore`.
- **Atom feed:** `scripts/build-feed.mjs` writes `.site/feed.xml`, linked from `index.html`. "Recently touched" comes from one batched `git log --name-only` walk over the vault (not one `git log` spawn per note) that records each note's most recent commit date; the newest 30 written lessons by that date become the entries, linking to their static pages.
- **Progressive Web App:** `manifest.json` + `sw.js` + the two icons make the site installable and give it limited offline support. `sw.js` precaches the app shell (every file `main.js` imports statically, including `views.js` and `benches/kit.js`, plus `theme.js`, the stylesheet and the two main fonts) and `content.json`, and runtime-caches lesson bodies (`content/<id>.json`) stale-while-revalidate as they are visited; a bench's own module is lazy-loaded and not precached. On a first visit the lesson on screen was fetched before the worker took control, so `main.js` asks for it again on `controllerchange`. The shell is served cache-first, so bump `CACHE_VERSION` in `sw.js` whenever a shell file changes.
- **Accessibility:** real links and buttons throughout, a skip link, route changes announced through `#announce` with focus moved to the page's `h1`, 44px touch targets, status marks that carry a text label (`aria-label`) and differ in shape as well as colour, and `prefers-reduced-motion` honoured (no smooth scrolling).

## Benches (interactive demos in lessons)

A **bench** is a small simulation embedded in a lesson (sliders, draggable points, step-throughs). Benches only simulate; the explanation lives in the note.

- **Note syntax:** a fenced block whose language is `bench`:

  ````
  ```bench
  id: dot-product
  title: Dot product playground
  fallback: One sentence describing the bench for readers without JavaScript.
  ```
  ````
  `id` (lowercase letters, digits, dashes) must match `.site/benches/<id>.js`; the build warns if it does not. Follow the block with a **Try this** list (3–4 experiments) and a **What you should notice** paragraph, written in the note.
- **Module contract:** `export default function mount(root, kit) { …; return cleanup; }`. `kit` is `benches/kit.js`: `h` (DOM), `frame`, `canvas` (DPR-aware, redraws on resize and theme change), `plot` (data-to-pixel mapping with axes), `slider`, `button`, `toggles`, `choice`, `stepper` (step/play/reset; never autoplays), `sorter` (click or drag items into bins, with a check), `reveal`, `stats`, `live` (screen-reader announcements), `dragHandles`, `rng` (seeded, for reproducible demos), `palette` (theme colours read from CSS variables: `ink`, `muted`, `accent`, `soft`, `soft2`, `white`, plus `warm` and `good`, which switch with the theme), `fmt`. `benches/grid.js` is shared code, not a bench: grid layout, stepwise BFS/DFS/A*/greedy search and wall painting for the Classic AI benches. `benches/mathkit.js` is shared code for the Math benches: world-to-pixel views, arrows, function curves, 2×2 matrix controls and grid warping, heat maps, and probability, statistics and polynomial-fitting helpers (pure functions, so notes' worked numbers can be computed with them in Node); `benches/network-kit.js` holds the tiny-network maths and diagram shared by the two network benches; `benches/mlkit.js` is shared code for the Machine Learning benches: seeded toy datasets (blobs, moons, ring), ridge/lasso/logistic/SVM/kNN learners, decision trees, forests, boosting stumps, k-means, hierarchical clustering, PCA, EM, a grid world with value iteration and Q-learning, and bandits (pure functions, so the notes' numbers can be computed in Node); `benches/rlkit.js` draws the grid world; `benches/dlkit.js` is shared code for the Deep Learning benches: activations, a tiny dense network and convolution/pooling, vanilla RNN/LSTM/GRU cell steps, softmax, and seeded toy "images" (pure functions, so the notes' numbers can be computed in Node); `benches/nnkit.js` is shared code for the Neural Networks benches: Hopfield network storage/settling/energy, Boltzmann machine sampling and contrastive divergence, leaky integrate-and-fire spiking neurons, self-organizing-map and competitive-learning updates, Gaussian RBF features and a least-squares solver, and the modern (softmax) Hopfield update that is mathematically attention (pure functions, so the notes' numbers can be computed in Node); `benches/tfkit.js` is shared code for the Transformers benches: BPE/WordPiece training and tokenization, patchifying, token embeddings, LayerNorm/RMSNorm, a plain and a gated (SwiGLU/GeGLU) feed-forward sublayer, self- and cross-attention, causal/padding/windowed masks, RoPE and ALiBi, a Mixture-of-Experts router, tensor-parallel splitting, graph adjacency/shortest-paths, and the quadratic- and linear-order attention computations plus online softmax (pure functions, so the notes' numbers can be computed in Node); `benches/gakit.js` is shared code for the Generative AI benches: decoding algorithms (greedy, beam search, temperature/top-p/top-k sampling, repetition and length bias, grammar masking, majority voting, induction-head-style copy completion), an exact score of a Gaussian mixture underlying a toy diffusion sampler (classifier and classifier-free guidance, ControlNet-style structural locking, lerp/slerp latent interpolation), image helpers (nearest/bilinear upsampling, harmonic inpainting and ridge-regularized outpainting, Gram-matrix style transfer), audio synthesis (phase-continuous sine frames), video/3D/code helpers (temporal-consistency damping, signed-distance smooth-min blending, brute-force program synthesis), multimodal helpers (codebook quantization, cosine similarity), evaluation metrics (perplexity, BLEU/ROUGE, a diagonal Fréchet distance, average pairwise distance, Elo rating), and risk/practice helpers (n-gram overlap detection, a green-list/red-list watermark, LoRA-style low-rank updates, a FLOPs→energy→carbon cost chain) (pure functions, so the notes' numbers can be computed in Node). Vanilla canvas/SVG only, no external requests, no dependencies.
- **Loading:** `main.js` (`mountBenches`) imports a bench when its placeholder scrolls near the viewport and mounts it into `.bench[data-bench]`; the placeholder text is the fallback, and a failed import leaves it with a "could not load" note.
- **Layout and text:** `frame(root, { title })` gives a title and two panes: visuals (canvas, grids, sorters, tables, lists) on the **stage**, controls and one readout strip in the **panel**; `body.append(...)` routes nodes automatically (add class `stage` to force one into the stage). Wide screens show them side by side (the canvas stays in view while you drag sliders); small screens stack them. Benches carry **no explanatory prose**: no hint line, no live lesson sentences. Explanation belongs in the note ("Try this", "What you should notice"); a bench shows a title, self-explanatory labels, numbers, and feedback for an action (the sorter's result, a rule engine's derived facts). Text that only helps screen-reader users goes through `live()`.
- **Colours:** bench code and the bench block in `styles.css` read a small set of compatibility variables (`--accent`, `--soft`, `--soft2`, `--white`, `--font`, `--pre`, `--warn-fg` and the `--r-*` names). `styles.css` maps each of them onto the site tokens in `:root`; restyle benches there, not in the 500-odd modules.
- **Rules:** benches must be operable by keyboard (every draggable quantity also has a slider), announce results via `live`, use theme colours (never hard-coded light ones), honour `reduceMotion`, and work at phone width. Add a bench with the note that uses it, then run `npm run test:benches` (it also checks for horizontal overflow at three widths).

## Lesson template (for notes that publish well)

One lesson answers one question. Every written lesson follows this arc, about 700–1500 words (concept lessons land near 700–950; longer only when the lesson needs it):

1. Summary paragraph (becomes the lesson summary and the lede), then **You need:** links to prerequisites that exist (shown as chips).
2. The question it answers → intuition (plain language, an analogy) → definition and notation → a worked example with small numbers.
3. **Bench** with **Try this** and **What you should notice**.
4. Where it appears in AI → common pitfalls → **Quick check** (3 questions, answers in `<details>`) → **Key terms** (3–6 short definitions) → **Related** links.

The site has no LaTeX renderer: write formulas in Unicode inside code fences (`a · b = a₁b₁ + a₂b₂`).

## Content pipeline rules

- Courses are configured in `.site/courses.json`, in learning order; adding one means adding an entry there (a folder course needs `folder` and `index`; a single-note course lists `notes`) and a line in the root `.gitignore` for its generated directory. The build warns about notes not assigned to any course.
- A course's index note sets the order of its chapters by its links; a chapter's landing note (same name as its folder) is the chapter intro and sets the order of its lessons the same way.
- Status is derived: empty → `outlined`, link-list only → `index`, otherwise `written` (frontmatter `status` overrides).
- Wiki links resolve by note title, case-insensitively; a link to a course's title resolves to that course's page.
- A lesson's **You need:** prerequisites in the same course must come earlier in that course; the build warns otherwise. Cross-course links go backwards only.
- Do not put knowledge in `.site/`. If the site needs different content, change the notes (with approval) or the pipeline.
